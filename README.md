# Simple REST API (Django REST Framework)
[![CI](https://github.com/haxily/simple-rest-py/actions/workflows/ci.yml/badge.svg)](https://github.com/haxily/simple-rest-py/actions/workflows/ci.yml)

A small, complete REST API built to learn API design in Python with Django REST Framework.

## What it demonstrates
- **CRUD** with a DRF `ModelViewSet` and router
- **JWT authentication** (SimpleJWT): public reads, authenticated writes
- **Validation** with clear per-field `400` errors
- **Filtering, search, ordering and pagination** (django-filter)
- **OpenAPI docs** with Swagger UI and ReDoc (drf-spectacular)
- **Docker** setup: gunicorn + PostgreSQL 17, configured through environment variables
- **Tests and CI**: pytest + coverage, run by GitHub Actions on every push and PR

**Stack:** Python · Django 6 · Django REST Framework · PostgreSQL / SQLite · Docker · pytest · GitHub Actions

## Quick start

### Option 1: Docker (PostgreSQL)
```bash
git clone https://github.com/haxily/simple-rest-py.git
cd simple-rest-py
cp .env.example .env          # then set the secret key and password
docker compose up --build
docker compose exec web python manage.py createsuperuser
```
Open http://localhost:8000/api/docs/. Migrations run automatically on start-up. Data is stored in
the `pgdata` volume (`docker compose down -v` wipes it).

### Option 2: Local (SQLite)
When `POSTGRES_DB` is not set, the project falls back to SQLite, so no database setup is needed.
```bash
git clone https://github.com/haxily/simple-rest-py.git
cd simple-rest-py

python3 -m venv .venv          # Windows: py -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cd djangorest
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```
The API is now at http://127.0.0.1:8000/api/ (the browsable API root).

## Endpoints
The HTTP method decides the action:

| Method | URL | Action | Auth |
|---|---|---|---|
| GET | `/api/users/` | List users | Public |
| POST | `/api/users/` | Create a user | JWT |
| GET | `/api/users/{id}/` | Retrieve a user | Public |
| PUT | `/api/users/{id}/` | Replace a user | JWT |
| PATCH | `/api/users/{id}/` | Partially update a user | JWT |
| DELETE | `/api/users/{id}/` | Delete a user | JWT |

Example body for POST / PUT:
```json
{ "name": "Peter", "age": 25 }
```

### Validation
- `name`: required, max 100 characters, surrounding whitespace trimmed, must contain at least one letter.
- `age`: required integer between 0 and 150.

Invalid requests return `400` with per-field error messages.

### Filtering, search & pagination
List responses are paginated (10 per page by default, max 100):
```json
{ "count": 14, "next": "http://localhost:8000/api/users/?page=2", "previous": null, "results": [...] }
```

| Query param | Example | Meaning |
|---|---|---|
| `name` | `?name=pet` | Name contains (case-insensitive) |
| `min_age` / `max_age` | `?min_age=18&max_age=30` | Age range (inclusive) |
| `search` | `?search=pet` | Search by name |
| `ordering` | `?ordering=-age` | Sort by `id`, `name` or `age` (`-` for descending) |
| `page` / `page_size` | `?page=2&page_size=5` | Pagination |

Params can be combined, e.g. `/api/users/?min_age=18&ordering=name&page_size=5`.

## Authentication
Get a token pair with the superuser you created, then send the access token as a `Bearer` header:
```bash
curl -X POST http://localhost:8000/api/auth/token/ \
  -H "Content-Type: application/json" \
  -d '{"username": "admin", "password": "<password>"}'
# -> {"refresh": "...", "access": "..."}

curl -X POST http://localhost:8000/api/users/ \
  -H "Authorization: Bearer <access>" \
  -H "Content-Type: application/json" \
  -d '{"name": "Peter", "age": 25}'
```

| Endpoint | Purpose |
|---|---|
| `POST /api/auth/token/` | Get an access (30 min) + refresh (1 day) token pair |
| `POST /api/auth/token/refresh/` | Exchange `{"refresh": "..."}` for a new access token |
| `POST /api/auth/token/verify/` | Check whether `{"token": "..."}` is valid |

In the browsable API, use the **Log in** link (top right) instead.

> **Note:** the accounts that log in are Django's built-in `auth.User`. The `/api/users/` resource
> is the app's own `api.User` model (the data being managed). They are separate tables.

## API docs
Interactive OpenAPI docs are generated by drf-spectacular:

| URL | What |
|---|---|
| `/api/docs/` | Swagger UI (click **Authorize** and paste a JWT access token) |
| `/api/redoc/` | ReDoc |
| `/api/schema/` | Raw OpenAPI 3 schema (YAML) |

## Tests & CI
From the repo root:
```bash
pip install -r requirements-dev.txt
pytest                                        # run the suite
pytest --cov=api --cov-report=term-missing    # with coverage
```
GitHub Actions (`.github/workflows/ci.yml`) runs Django system checks, a missing-migrations check,
OpenAPI schema validation and the test suite on every push to `main` and every pull request.
